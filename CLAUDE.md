# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Drovia is a macOS 26+ menu-bar app (Swift 6, strict concurrency, SwiftUI + AppKit): the user drags files, holds a modifier (⇧ Convert, ⌘ Tools, ⌃ Actions, ⌥ Recipes) and drops them on a radial wheel of file actions. It's also reachable with ⌃⌥D on Finder's selection and from two Shortcuts actions. See README.md for the feature list and permissions.

## Commands

The Xcode project is generated by XcodeGen from `project.yml` and is not committed. Don't edit `Drovia.xcodeproj`; after adding or removing files run `make gen` (the other targets do it).

```sh
make run          # build Debug and launch (kills a running Drovia first)
make test         # all unit tests
make lint         # SwiftFormat check, as CI runs it; `make format` fixes
make release      # Release build (hardened runtime) in build/Build/Products/Release
make logs         # stream the app's os_log (subsystem com.arvesso.drovia)
python3 Scripts/missing-strings.py   # localizable strings without a Russian translation
```

One suite or test (Swift Testing; note the `()` for a single test):

```sh
xcodebuild -project Drovia.xcodeproj -scheme Drovia -destination 'platform=macOS,arch=arm64' \
  -derivedDataPath build test -quiet -only-testing:DroviaTests/RecipeTests
# …-only-testing:'DroviaTests/RecipeTests/chainsStepsAndNamesResultAfterRecipe()'
```

Tool versions are pinned in `.swiftformat_version` and `.xcodegen_version`; CI installs exactly those and `make` warns when local ones differ (SwiftFormat versions indent some code differently). CI (`.github/workflows/ci.yml`) runs lint, `make test` and `make release`.

## Architecture

**Drag → wheel → action.** `DragMonitor/DragSessionMonitor` notices system-wide file drags without Accessibility permission: global mouse events start a press, then a timer polls the drag pasteboard's change count. `Wheel/WheelCoordinator` ties it together: `ModifierWatcher` picks the wheel kind, `ActionRegistry.actions(for:types:layout:recipes:)` fills it, `WheelPanel` shows it, and a drop on a sector (resolved by `DroppedFiles`, including promised files from Safari/Mail written to a temp folder) goes to `ActionRunner.run`. Drags started by Drovia itself (shelf, onboarding) go through `beginInternalDrag`/`endInternalDrag` so the monitor doesn't treat them as external.

**Folder access gate.** Drovia isn't sandboxed but must not touch files outside folders the user allowed (`FolderAccess`, `FolderScope`), or with Full Disk Access. Nothing reads a dragged file (not even a thumbnail) before `folderAccess.allows(...)` passes, since that could trigger a privacy prompt mid-drag. Shortcuts inputs are checked the same way.

**Actions.** Every wheel item implements `DroviaAction` (`Actions/DroviaAction.swift`). `supports(_:)` decides from file types only, never by reading files (it runs during the drag). Variants for different file kinds share a `sectorID`, so they're one sector for ordering and hiding. Actions are `@MainActor`; heavy work lives in `Engines/` (ImageIO, PDFKit, AVFoundation, Vision, libwebp, `tar`/`ditto`), which are synchronous or nonisolated async and run off the main actor, usually via `ActionContext.processEach` (parallel, results in input order, concurrency capped by cores and memory). Command-line tools go through `Engines/Subprocess` (drains pipes, terminates on cancellation).

**The runner and the guarantees.** `ActionRunner.execute` is shared by the wheel and Shortcuts (`allowsPrompts`/`ActionContext.canAskUser` false for Shortcuts). It enforces README's promises, so keep them when changing actions:
- Destinations come from `context.planner` (`OutputPlanner`): naming template, output folder, unique names reserved case-insensitively. Never write next to a file without it, never overwrite.
- An action reports `ProcessedFile(source:output:)`; `output == nil` means "left unchanged". The runner adds undo steps for created files, trashes originals when that setting is on (via the injected `Trash`), records `HistoryStore` entries and adds results to the shelf.
- Half-written outputs are removed on failure (`removingOnFailure`), since failed results aren't in history.

**Recipes** (`Recipes/`) chain sector IDs, Shortcuts and zsh scripts. `RecipeAction` runs intermediate steps into temporary folders and only the last file-making step writes where results go; `types(after:given:)` predicts what each step turns files into so the wheel only offers recipes that can run. Script steps run only if approved (`ScriptApprovals`: HMACs under a keychain key; typing in the recipe editor approves), because the preferences file they live in is writable by any process.

**Editor** (`Editor/`): `EditorModel` (crop, annotations, background, undo snapshots) renders through `EditorRenderer`, the same code for the downscaled on-screen preview and the saved full-size image; saved images are handed to the action one by one (`onSave`).

## Conventions

- **Localization:** every user-facing string goes in `Drovia/Resources/Localizable.xcstrings` with English and Russian (plural variations for counts: one/few/many/other); Info.plist strings in `InfoPlist.xcstrings`. The project is built from the CLI, so the catalog is never synced automatically: add keys by hand and run `Scripts/missing-strings.py`.
- **Tests** (Swift Testing, `DroviaTests/`) run inside the real app as test host, so they must never touch the developer's real state. Use the helpers in `NamingTemplateTests.swift`: `TemporaryFolder`, `TestDefaults` (in-memory `UserDefaults`; on-disk suites leave plists that cfprefsd rewrites), `TestTrash` (pass to `HistoryStore`/`ActionRunner`) and `TestScriptKey` (pass to `SettingsStore`). Test contexts use `canAskUser: false` so no modal dialog can block a run. Fixtures are generated in code (see `ImageEngineTests`, `MediaEngineTests`).
- Drag and drop, the wheel and the menu bar can't be unit-tested; say in PRs what needs a manual check.
- Comments explain why, briefly; match the existing density and naming.
- **Pull requests and issues** are written in English and follow `.github/PULL_REQUEST_TEMPLATE.md` and the forms in `.github/ISSUE_TEMPLATE/` (Problem / Change / Tests / Please check by hand). Label issues with one type, one area and a priority as described in CONTRIBUTING.md; `unconfirmed` marks problems seen in code but not reproduced. Branch from `main` with a prefix for the kind of change (`fix/`, `perf/`, `security/`, `design/`, `test/`, `docs/`, `build/`); never commit to `main` directly.
- Builds are ad-hoc signed by default; `make signing` writes the developer's team to `Config/Local.xcconfig` (not committed) so TCC grants and keychain access survive rebuilds.
